## 提示词正文

### 1. 卡片有效性核对

- 卡片"文件清单"中标为**既有**的路径必须存在（`ls`）；不存在即停，报告"卡片失效：路径 X 不存在"。
- 卡片引用的 `RunManager` 等行号以 commit `d9653a0` 为基线；若代码已漂移，按语义定位（"写完 feedback 之后、cooldown 之前"），不要按行号硬套，并在报告里注明实际行号。
- `dodCommands` 里的每条命令先确认能被解析（`--help` 存在、路径存在）。

### 2. TDD 纪律（逐个 DoD 垂直切片，不要先写全部测试再写全部实现）

对卡片 §9 列出的每个测试场景：

1. **RED**：先写这一个测试，运行，确认失败且失败原因是"功能未实现"而不是编译错误或测试写错。命令：`mvn -q -Dtest=<TestClass>#<方法名前缀>* -Djacoco.skip test`。
2. **GREEN**：写**最少**的实现让它通过。不为后面的测试提前写代码。
3. **REFACTOR**：只在 GREEN 后重构；重构后重跑该测试类。
4. 下一个场景。

测试规范：
- 测试类与被测类同包同路径（`judge/RulesJudge` → `judge/RulesJudgeTest`）；端到端放 `integration/`。
- 方法名用中文描述行为（仓库惯例，如 `子进程读stdin到EOF_不会等到超时`），断言用 AssertJ。
- 测试只经公开接口断言可观察行为：文件产物、`report.json` 字段、trace 事件、返回值、退出码。不 mock 内部协作者，不测私有方法。
- 需要临时夹具用 `@TempDir`；需要任务规格用 `testsupport/TestSpecs`；需要真实任务用 `tasks/api-payload-001` 等内置任务。
- 每个 DoD 勾选项至少对应一个断言；卡片测试覆盖矩阵（`docs/11`）里属于本卡的行都要有对应测试。

### 3. 硬约束（违反任何一条 = 本卡失败，不要"顺手"）

- **不动判分内核**：`SubmissionManager` / `JudgeRunner` / `RulesJudge` / `ScriptJudge` 的判分逻辑不改。允许改的只有卡片 In-scope 明确列出的文件。
- **合约冻结**：MCP 工具的 name / inputSchema / 返回顶层字段 / 错误码以 `EnvironmentToolSpecs` + `src/test/resources/mcp/tools-list.snapshot.json` 为准；要改必须先更新快照并在报告里说明理由。
- **trace 可信链**：新事件必须同步 `TraceEventType` 枚举 + `schemas/trace.event.schema.json` + `TraceLoggerTest`；只能用 `RunManager` 交出的那一把 `TraceLogger`，禁止再 `TraceLogger.open`；判分只认 HMAC 可核验事件。
- **hidden 禁区**：expected、judge 规则、mock 应答不出现在 `work/`、`samples/`、instructions、feedback、文档、测试断言字符串、提交信息里。
- **stdio 纪律**（03 及之后）：stdout 只走单行 NDJSON 协议帧；日志走 stderr。
- **不做 Out-of-scope 的事**：发现相邻问题写进报告"顺带发现"，不改。
- **生成物不入库**：`target/`、`runs/`、`/tmp/*` 不 `git add`；新增类后 `bash bin/gen-codemap.sh` 重新生成 `docs/CODEMAP.md` 并一起提交。

### 4. 端到端验证（GREEN 之后、提交之前，缺一不可）

按顺序执行并把每条的实际输出摘要写进报告：

1. 卡片 `dodCommands` 逐条运行，全部 exit 0。
2. `bash bin/gen-codemap.sh --check`（新增 / 改名类时）。
3. `mvn -q -B verify`（含 Checkstyle、JaCoCo 覆盖率门禁；期望 0 fail / 0 error）。
4. 卡片属于安全敏感面（trace / tool / PathGuard / 红队 / Docker）时：`bash redteam/test_gate.sh && bash redteam/run_all.sh`，红队 VULNERABLE 不得超出登记基线（Docker 就绪 0 / 回退 1）。
5. 有 CLI 或传输层改动时，跑一条**真实路径**而不只是单测：例如 `bin/agent-eval mcp-serve --task tasks/api-payload-001 --runs-root /tmp/e2e < /dev/null`，或按卡片写明的真实 client（Codex `mcp_servers`）跑一次，贴出 `report.json` 的 `run.status / run.adapter / attempts`。
6. 提交前：`bash bin/ci-smoke.sh`（本轮已跑过 `mvn verify` 可用 `SKIP_TESTS=1`）。
7. `git diff --check`。

任一步失败：修，回到第 2 节，不要跳过、不要注释掉测试、不要放宽断言。

### 5. 提交

- 每张卡一个或少数几个 commit；信息格式：`{{CARD_ID}}: <一句话做了什么>`；实跑发现并修的框架问题单独 commit，前缀 `{{CARD_ID}} 发现修复:`。
- 提交内容只含 In-scope 文件 + `docs/CODEMAP.md`（若变）+ 卡片状态回写。
- 回写状态：卡片 frontmatter `status: done`；对应索引（`docs/11` 或 `docs/09`）状态列改"完成"；设计文档相应章节补"已实施"或决策记录（卡片 DoD 若要求）。
- 不 push，除非用户明确要求。

### 6. 遇到歧义 / 阻塞

- 先按设计文档判据裁决；能裁决就做，并在报告"决策"段写明依据。
- 裁决不了（两种读法会导致不同实现）：**停下来**，列出两种读法、各自影响、你的建议，等回复。不要猜一个做下去。
- 外部阻塞（凭证过期、Docker 未起、client 未安装）：完成所有不依赖它的 DoD，报告里明确"未完成项及原因"，不要标 done。
